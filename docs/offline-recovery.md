# 停止時バックアップと隔離復元の手順案

対象は Agent Guild のローカルデモ（SQLite schema 2）です。[Issue #10](https://github.com/maasa1221/agent-guild/issues/10) の復旧・停止・ロールバック確認に向けた資料で、第三者向け運用の開始承認ではありません。実サービスの停止権限、保存先、保持期間、復旧目標、連絡先は未決です。

## 合成データで再現できる範囲

`node --test server/backup.fixture.test.mjs` を実行します。テストは OS の一時ディレクトリで store を閉じてからデータディレクトリ全体をコピーし、別の場所で Issue、回答、採用回答、模擬報奨金、監査履歴と SQLite の整合性を確認します。復元先を変更した後にも、元のバックアップから**別の隔離先**へ復元できることを確認します。DB 欠落・破損は拒否します。テスト終了時に合成データは削除されます。

2026-10-13 の WSL 実測は **1/1 pass**（テスト本体 42.8 ms）でした。この時間は実データの RTO ではありません。

`server/backup.test.mjs` は、`deploy/backup.sh` が呼ぶ処理関数（`deploy/backup-lib.sh`）を一時ディレクトリと偽の `systemctl` で実行します。検査済みのコピーだけが世代として残ること、2 つの隔離先へ同じ状態と監査履歴を復元できること、DB の欠落・破損・対応外 schema・コピー失敗で以前の世代が残ること、保持世代数の 0 や不正値をサービス停止前に拒否すること、開始時に動いていたサービスだけを起動し直すことを確認します。本番の固定パス、実 systemd、本番 DB には触れません。2026-10-16 の WSL で `node --test --test-concurrency=1 server/backup.test.mjs server/backup.fixture.test.mjs` を実行し、**14/14 pass** でした。

これは稼働中の DB のバックアップや、実データ規模での所要時間・復旧目標を検証しません。実資金と実 OAuth grant も扱いません。

## 運用先が決まった後の確認順

1. **対象と停止責任者を確認する。** 対象環境、コードの commit、データディレクトリ、書き込みを止める手段、停止を判断する人、利用者への連絡先を記録する。未確定なら実環境の操作に進まない。
2. **書き込みを止め、プロセスの終了を確認する。** 停止が確認できてから `data/` 全体を保護された別の場所へコピーする。`listings.sqlite` だけを稼働中にコピーしたものを正常なバックアップとみなさない。SQLite の `-wal` / `-shm` と旧 JSON 原本・移行バックアップも含め、元データは変更しない。
3. **隔離した復元先を事前検査する。** バックアップを隔離先へコピーし、起動前に `node server/verify-backup.mjs <隔離先>` を実行する。この検査は読み取り専用で DB を作成・移行せず、`listings.sqlite` が通常ファイルとして存在すること、`PRAGMA integrity_check` が `ok` であること、schema 2 であること、必要な表と列、外部キーの整合、保存データ（JSON）と監査履歴をアプリと同じ読み取りで読めることを確認する。出力は `verify-backup: ok schema=2 listings=… answers=… audit=…`（件数のみ）か、`verify-backup: failed phase=<段階>` で、保存内容や利用者 ID は表示しない。件数と、期待する Issue・回答・採用状態・監査履歴が一致することを確認する。DB が欠けたまま `openStore` を先に呼ぶと空 DB を作り得るため、この検査を先に行う。検査不能・不一致なら復元を成功扱いせず、書き込み停止を維持する。
4. **隔離先で起動・再起動する。** 読み取りと権限境界、mock 支払表記、監査履歴を確認する。実環境への切替は、復旧担当者がチェック結果と失われ得る更新を確認してから決める。
5. **切り戻しが必要なら別の隔離先で先に再現する。** 失敗したデータを保全し、復元前に取得したバックアップと対応するコード版を組として選ぶ。旧 JSON は DB 作成後の更新を含まないため、現行 DB の代替として無条件に再移行しない。schema の後方互換が確認できない場合は旧コードを直接起動しない。データとコードの整合性が確認できなければ停止を維持し、責任者へ判断を戻す。

## 記録と未決事項

| 項目 | 記録する内容 |
| --- | --- |
| 対象 | 環境、コード commit、schema version、元データと隔離先の識別子 |
| 停止・復旧 | 判断者、実施者、停止時刻、コピー完了時刻、再開可否と時刻 |
| 検証 | DB 存在、整合性、Issue/回答/採用状態/監査の照合結果、再起動結果 |
| 失われる更新 | バックアップ取得時点以降の差分、利用者への連絡と承認 |
| 本番化前の判断 | バックアップ頻度・保持期間・アクセス権、RPO/RTO、監視、問い合わせ窓口、停止・復旧責任者 |
